## レキサー(字句解析器)とは

- **入力**:ただの文字の並び(ソースコード)
- **出力**:意味の単位に分けたトークンの列
- 文法が正しいかは気にしない。`let = = 5 let` でもトークンに分けられれば仕事は終わり。文法のチェックは第2章のパーサの役目。

## `let five = 5;` をトークンに分ける

| 元の文字列 | 種類 |
| --- | --- |
| `let` | キーワード(予約語) |
| `five` | 識別子 |
| `=` | 代入 |
| `5` | 整数リテラル |
| `;` | セミコロン(区切り子) |
| (なし) | 入力の終わり(EOF) |

入力に書かれた5つに加えて、最後に「入力の終わり」のトークンが付く。

## トークンが持つ情報は「種類」と「元の文字列」

- `=` や `;` は種類がわかれば文字列も決まる。
- 識別子(`five` か `ten` か)やリテラル(`5` か `42` か)は、種類だけでは中身がわからない。
- だから `Token` には `Kind`(種類)と `Value`(元の文字列)の2つを持たせた。

## つまずいたこと1:種類と中身を混同した

最初は `five` 用、`5` 用の定数を作ってしまった。でも、そうすると `ten` や `10` が出るたびに定数が必要になる。ユーザーが書く名前や数は無限にある。

**国語の品詞と同じ**と考えたら理解できた。

| 単語(Value) | 品詞(Kind) |
| --- | --- |
| 私 | 名詞 |
| 本 | 名詞 |

- 「私」と「本」は単語が違っても品詞は同じ。
- `five` と `ten` も、`Value` は違っても `Kind` は同じ「識別子」。
- 定数の一覧(`const`)に並べるのは**分類の一覧**であって、単語の一覧ではない。

## つまずいたこと2:入力の終わり

- 最初は改行で終わりを伝えると考えた。でも、改行は入力の途中にもある(複数行のプログラム)ので、合図には使えない。
- 必要なのは、**入力のどこにも書かれていない特別なトークン**。一般に EOF(End Of File)と呼ぶ。
- 値を `""` にするのは避けた。Go のゼロ値も `""` なので、「値の入れ忘れ」と区別できなくなる。

## 見た目のない種類の値は「ラベル」でいい

- `+` は値を `"+"` のように見た目そのままにできる。
- 識別子・整数リテラル・EOF・不正な文字には決まった見た目がない。そういう種類の値は、分類名をそのまま文字列にした名札でいい。

## キーワードはまとめず、1つずつ別の種類にする

- 識別子は `five` も `ten` も同じ種類にまとめた。パーサにとって扱いが同じだから。
- キーワードは `let` なら代入の文、`if` なら条件分岐のように、**パーサの処理がキーワードごとに変わる**。だから1つずつ別の種類にする。
- レキサーは英字の並びを読んだあと、それが予約語の一覧にあるかを調べ、あればそのキーワード、なければ識別子として返す。

## 名前の付け方で学んだこと

- Go では**大文字で始まる名前だけ**がパッケージの外から見える。`Token` のフィールドが小文字だと、`lexer` から使えない。
- 型の名前は中身に合わせる。`Keyword` や `InputWord` だと「単語そのもの」に見えて混乱のもとになった。→ `TokenKind`
- 記号の定数は**意味ではなく見た目**で名付ける。`;` を「行の終わり」と呼ぶと、1行に2回出たときにおかしい。→ `Semicolon`
- `=` は「等しい」ではなく「代入」。将来 `==` と区別するため。→ `Assignment`
- 「リテラル」だけでは整数か文字列か区別できない。→ `NumberLiteral` / `StringLiteral`

## 種類を文字列で表す理由

- 文字列:テスト失敗時に `expected "識別子", got "+"` のように読める。学習向き。
- 整数(`iota`):比較が速くメモリも小さい。本格的な処理系でよく使われる。
